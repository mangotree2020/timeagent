# Gemini 일정 도우미 기준선

## 목적과 범위

같은 입력과 같은 판정 규칙으로 (1) 운영 `assistant` 회귀를 확인하고, (2) 후보 Gemini 모델을 비교한다. 실제 사용자 녹음과 개인정보는 사용하지 않는다. 평가셋은 합성 한국어 텍스트 21개이며, 사용자가 명시적으로 제공한 합성·사전 동의 M4A를 선택적으로 추가할 수 있다.

고정 사례는 상대 날짜, KST 자정 경계, 명시 날짜, 목적지 수정, 이동수단 동의어, 준비 행동 병합·삭제, 필수 항목 누락 질문, 다회 대화, 환각 차단, 현재 스키마가 지원하지 않는 반복 일정의 질문 fallback을 포함한다.

`clientContext`는 의도적으로 `nowIso`의 UTC 날짜(2026-08-16)와 현지 날짜(2026-08-17, 월요일)를 하루 어긋나게 둔다. 상대 날짜를 UTC로 푸는 모델은 이 평가셋에서 반드시 드러난다.

## 실행

운영 회귀(모델을 지정하지 않으면 운영 `assistant`가 설정된 모델로 답한다):

```bash
npm run benchmark:assistant
```

모델 비교. 격리된 `assistant-benchmark` 함수를 먼저 배포해야 하며(아래 참고), 인증 토큰이 필요하다.

```bash
ASSISTANT_BENCHMARK_URL="https://<project>.supabase.co/functions/v1/assistant-benchmark/v1/schedule/turn" \
ASSISTANT_BENCHMARK_TOKEN="<supabase anon JWT>" \
ASSISTANT_BENCHMARK_MODELS="gemini-3.1-flash-lite,gemini-3.5-flash-lite,gemini-3.6-flash" \
ASSISTANT_BENCHMARK_REPEATS=1 ASSISTANT_BENCHMARK_ATTEMPT_START=1 \
npm run benchmark:assistant > tmp/attempt1.json
```

한 회차는 모델 수 × 사례 수만큼 호출한다. 3모델 × 21사례는 약 3분이므로, 반복은 `ASSISTANT_BENCHMARK_ATTEMPT_START`를 1, 2, 3으로 바꿔 회차별 명령으로 나눠 실행한 뒤 하나로 합친다. 합치기는 평균의 평균이 아니라 전체 run을 다시 집계한다.

```bash
node scripts/benchmark-gemini-assistant.mjs --merge tmp/attempt1.json tmp/attempt2.json tmp/attempt3.json > tmp/gemini-benchmark-3models.json
```

합성 M4A를 포함하려면 `ASSISTANT_BENCHMARK_AUDIO=/absolute/path/to/consented-fixture.m4a`를 추가한다.
한 사례만 재확인할 때는 `ASSISTANT_BENCHMARK_CASES=fixture-id`를 추가한다. 결과에는 선택된 fixture 내용과 모델 목록을 해시한 `suiteFingerprint`가 기록되며, 병합 시 이 값과 모델 목록이 다르거나 같은 attempt가 중복되면 거부한다.

결과 JSON에는 사례 ID, 판정 결과, 지연, 토큰 사용량만 남는다. 응답 본문, transcript, assistantMessage는 저장하지 않는다. 이 성질은 `scripts/benchmark-gemini-assistant.test.js`가 검사한다.

### 격리된 벤치마크 함수

`supabase/functions/assistant-benchmark/`는 운영 `assistant`의 트윈이다. 상시 배포하지 않으며 비교가 필요할 때만 올리고 끝나면 지운다. 운영과 다른 점은 세 가지뿐이다.

1. 모델을 요청 본문에서 받고 허용 목록에 있는 값만 받는다.
2. `verify_jwt = true`로 배포한다. 인증된 호출자만 Gemini 할당량을 쓸 수 있다.
3. 기본값도 환경변수 fallback도 없다. `GEMINI_SCHEDULE_MODEL`을 읽지 않으므로 운영 모델 설정이 벤치마크 결과의 모델을 대신 정할 수 없다.

응답 검증 함수는 운영본과 바이트 단위로 같아야 하며, `scripts/assistant-benchmark-contract.test.js`가 어긋나면 실패한다. 운영보다 느슨하거나 엄격한 계약으로 모델을 비교하면 앱이 실제로 쓰지 않는 기준으로 고른 결과가 되기 때문이다.

## 판정과 비용 계산

- 구조화 성공: HTTP 200, 운영 Edge Function의 JSON 응답 검증 통과, 토큰 사용량 존재.
- 사례 통과: 그 사례가 요구한 모든 검사를 통과. 하나라도 어긋나면 실패다.
- 필드 정확도: fixture가 지정한 날짜·시간·enum·준비 행동·질문 여부·`readyToApply`·`entryType`의 정확 일치. 목적지만 `서울시청`과 `서울 시청` 같은 공백 차이를 동일하게 본다. 사용자가 말하지 않은 항목은 비어 있어야 하며, 이동수단의 앱 기본값 `AI 추천`은 초안을 그대로 되돌려준 것이므로 채워지지 않은 값으로 센다.
- 응답을 받지 못한 요청도 그 사례의 모든 검사를 놓친 것으로 센다. 실패한 모델이 답을 낸 모델보다 높은 필드 정확도를 받을 수 없다.
- 지연: 클라이언트 요청 시작부터 JSON 수신까지 wall-clock 밀리초. p50/p95는 nearest-rank이며 구조화 성공한 요청만 표본에 넣는다. 빠른 실패가 빠른 응답으로 보이지 않게 한다.
- 비용: modality별 입력 토큰과 출력·사고 토큰에 표준 유료 단가를 적용한다. 무료 tier와 배치·Flex 할인은 반영하지 않는다. 단가가 없는 modality가 섞인 요청은 추정하지 않고 비용 미상으로 남긴다.
- 모델을 지정했는데 응답이 다른 모델로 표시되면 그 요청은 점수를 매기지 않고 하네스 실패로 기록한다. 요청이 격리 함수가 아닌 다른 엔드포인트에 닿았다는 뜻이므로 어느 모델의 측정으로도 쓸 수 없다.
- 실패는 세 가지로 나눈다. `model`은 모델이 답했지만 운영 계약을 어긴 경우, `harness`는 우리 요청·인증·모델 접근 권한 문제, `infrastructure`는 타임아웃·rate limit·5xx다.

### 실패 항목 9건

189 요청 모두 HTTP 200과 운영 계약을 통과했다. `harness` 실패와 `infrastructure` 실패는 0건이며, 하네스나 응답 스키마가 특정 모델과 맞지 않아 생긴 실패는 없다. 9건 전부 모델이 낸 값 자체가 틀린 경우다.

| 어긋난 검사 | 건수 | 모델 | 내용 |
|---|---:|---|---|
| `date="2026-08-18"` | 6 | 3.5-lite 3, 3.6-flash 2, 3.1-lite 1 | `내일`을 현지 날짜 2026-08-17이 아니라 `nowIso`의 UTC 날짜 2026-08-16 기준으로 풀어 2026-08-17로 하루 당겼다. 재현 확인함. |
| `question=true` | 2 | 3.1-lite 2 | 잡담(`오늘 좀 피곤하네`)에 되묻기는 했으나 `question` 필드를 null로 두어 앱이 다음 질문을 읽을 수 없다. |
| `transport="도보"` | 1 | 3.5-lite 1 | `걸어서 갈게`를 `도보`로 정규화하지 못했다. |

세 모델이 공통으로 틀리는 항목은 UTC 기준 상대 날짜 하나이며 그것도 간헐적이다. 같은 입력을 다시 호출하면 대부분 2026-08-18로 맞게 답한다. 모델 선택이 아니라 system instruction의 상대 날짜 규칙을 더 강하게 못박는 쪽이 세 모델 모두에 효과가 있다.

`gemini-3.5-flash-lite`의 실패 4건 중 3건이 1회차에 몰려 있다. 회차 간 편차이며 3회 표본으로는 모델 간 순위를 가를 만한 차이가 아니다.

### Codex 교차 검증과 합성 음성 스모크

Codex가 `tmp/gemini-benchmark-3models.json`의 189개 run을 문서 집계와 별도로 다시 계산했다. 모델별 HTTP 상태·응답 모델 라벨·구조 성공·사례 통과·필드 수·p50/p95가 위 표와 모두 일치했고, 저장 결과에 응답 본문·전사문·오디오가 없는 것도 확인했다. 공식 가격표도 2026-08-17에 다시 열어 세 모델의 표준 유료 단가와 3.6 Flash 프로모션 기간을 교차 확인했다.

텍스트 결과만으로 음성 일정 기능을 판단할 수 없어서 macOS Yuna가 생성한 4.62초 한국어 M4A 한 문장(`내일 오후 세 시 서울시청에 지하철로 가고 자료 준비 십 분 추가해줘`)을 별도 스모크 테스트했다. 1사례 × 3모델 × 3회 = 9요청이며 실제 사용자 녹음이나 개인정보는 사용하지 않았다.

| 모델 | 구조/사례/필드 통과 | p50 | p95 | 평균 요청 비용 |
|---|---:|---:|---:|---:|
| gemini-3.1-flash-lite | 3/3, 15/15 | 3,177ms | 3,581ms | $0.001017 |
| gemini-3.5-flash-lite | 3/3, 15/15 | 7,547ms | 12,415ms | $0.002088 |
| gemini-3.6-flash | 3/3, 15/15 | 6,570ms | 6,681ms | 미상(공식 오디오 단가 없음) |

모두 날짜·시간·장소·이동수단·준비 행동을 맞혔다. 표본이 한 문장 3회뿐이라 일반적인 음성 품질 순위를 뜻하지 않지만, 현재 모델은 이 스모크에서 가장 빠르고 정확도 열세도 없었다. 첫 실행은 로컬 `jq` 부재로 인증 토큰이 비어 9건 모두 JWT 401이었으며 모델에 도달하지 않은 하네스 실패라 측정에서 제외하고, Node로 키를 파싱한 정상 실행만 위에 기록했다. 원본 측정은 `tmp/gemini-benchmark-audio-smoke.json`이다.

교차 검증에서 결과 병합의 재현성도 보강했다. 하네스는 선택 fixture와 문맥의 SHA-256 `suiteFingerprint`를 기록하며, fixture·후보 모델·오디오 포함 여부가 다른 결과 또는 같은 attempt가 중복된 결과를 병합하지 않는다.

## 추천

> 아래 추천은 3회 초기 비교 당시 기록이다. 최종 결정은 다음 `3.1/3.5 혼합 5,000건 비교` 절을 따른다.

**초기 비교에서는 기본값 `gemini-3.1-flash-lite`를 유지했다.**

- 품질 차이가 선택 근거가 되지 못한다. 세 모델의 사례 통과 격차는 63회 중 2건(95.2% vs 96.8% vs 93.7%)이고 필드 정확도 격차는 288개 검사 중 2개다. 이 표본에서 유의한 차이로 볼 수 없다.
- 비용 차이는 확실하다. `gemini-3.6-flash`는 2.5배($0.885 → $2.188/1,000건)이며 2027-01-01 단가로는 4.9배($4.375)가 된다. 사례 2건을 더 맞히려고 지불하기에는 크다.
- `gemini-3.5-flash-lite`는 p50이 324ms, p95가 365ms 빠르지만 비용이 23% 높고 이번 표본에서 통과율이 가장 낮았다. 지연이 제품 병목으로 확인되기 전까지 바꿀 이유가 없다.
- 세 모델 모두 p95가 3초 미만이고 구조화 성공률이 100%다. 운영 계약은 세 모델 어디에도 호환된다. 즉 이 선택은 되돌리기 쉽고, 나중에 비용이나 지연 요구가 바뀌면 같은 하네스로 다시 재기만 하면 된다.
- 합성 음성 스모크에서도 세 모델 정확도는 같고 3.1-flash-lite가 가장 빨랐다. 한 문장뿐이므로 보조 근거로만 사용한다.

다음에 손댈 곳은 모델이 아니라 프롬프트다. 실패의 3분의 2가 상대 날짜를 UTC로 푸는 한 가지 원인이며, `clientContext.localDate`를 오늘로 쓰라는 규칙이 이미 지침에 있는데도 간헐적으로 어긋난다. 이 규칙을 강화하고 같은 평가셋으로 재측정하면 세 모델 모두에서 개선을 확인할 수 있다.
