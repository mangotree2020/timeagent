# 개발 하네스

하네스는 에이전트나 개발자가 같은 입력, 명령, 화면 기준으로 변경을 검증하도록 만드는 실행 계약이다.

## 환경 고정

- Node.js: 20 이상, 현재 검증 v24 LTS
- 패키지 매니저: npm, `package-lock.json` 커밋
- Expo/React Native 버전: `package.json` 고정
- 설치: 로컬은 `npm install`, CI는 `npm ci`

## 한 번에 실행

```bash
npm run verify
```

이 명령은 다음을 순서대로 실행한다.

1. TypeScript strict typecheck
2. Expo ESLint
3. Jest 단위 테스트

## 개발 루프

```bash
npm start
npm run typecheck
npm test -- --watch
```

기능 구현 중에는 가장 가까운 단위 테스트를 먼저 돌리고, 작업 완료 전에 전체 `verify`를 실행한다.

## Android Maestro E2E

연결된 Android 기기에서 핵심 흐름 전체를 실행한다.

```bash
npm run e2e:android
```

빠른 smoke 태그만 실행할 때는 다음 명령을 사용한다.

```bash
npm run e2e:android:smoke
```

| Flow | 파일 | 검증 범위 |
|---|---|---|
| H-01 | `e2e/maestro/01_first_schedule.yaml` | 신규 설치, 온보딩, 첫 일정, 계획 확정, 예약 저장 |
| B-01 | `e2e/maestro/02_plan_b_confirmation.yaml` | Plan B 근거, 변경 확인, 명시적 적용 |
| J-01 | `e2e/maestro/03_location_denied_fallback.yaml` | 위치 권한 거부, 마지막 위치 경로, 재시도 fallback |
| L-01 | `e2e/maestro/04_personalization_learning.yaml` | 실제 시간 학습, 다음 계획 반영·제외, MVP 지표 생성·초기화 확인 |
| BG-01 | `e2e/maestro/05_background_permission_gate.yaml` | TMAP 실제 경로, 지도 스크롤, 화면 꺼짐 안내, 시스템 위치 권한 화면 진입 |

각 flow는 앱 상태를 독립 초기화한다. J-01의 UI fallback은 릴리스에서 비활성인 `__DEV__` fixture로 결정적으로 검증하며, 실제 Android 권한 팝업 거부는 수동 스모크에서 별도 확인한다. BG-01은 시스템 위치 권한 화면 진입까지만 자동화한다. 민감한 `항상 허용`은 자동 승인하지 않으므로 사용자가 Android 설정에서 직접 승인해야 한다.

## 접근성 점검

연결 폰의 현재 글자 배율을 기록한 뒤 200%로 변경하고 H-01을 실행한다.

```bash
adb shell settings get system font_scale
adb shell settings put system font_scale 2.0
maestro test e2e/maestro/01_first_schedule.yaml
```

검증 후에는 반드시 원래 배율로 복원하고 앱을 재시작한다.

```bash
adb shell settings put system font_scale 1.0
adb shell am force-stop com.timeagent.app
adb shell am start -a android.intent.action.VIEW -d ontime:/// com.timeagent.app
```

확인 기준은 시간·거리 단위 분리 없음, 핵심 CTA 스크롤 접근 가능, 타임라인 시각 한 줄 유지다. `npm run visual:test`에는 세 viewport의 온보딩 키보드 포커스·Space 실행도 포함한다. TalkBack 실제 읽기 순서·상태 변경 음성의 수동 검증은 사용자 요청으로 현재 작업 계획에서 제외한다.

## 고정 시나리오

- 목적지 선택: 새 일정에서 장소명 검색 → 목록 선택 → 최근 장소 저장·재선택 → 다음 단계 이동
- 지도 목적지: 지도 열기 → 위치 탭 → 주소 또는 좌표 확인 → `이 위치 선택`
- 음성 일정: 하단 내비게이션 가운데 음성 버튼 → AI 첫 질문·자동 듣기 → 발화 후 약 0.8초 침묵 자동 제출 → 추출 카드 확인 → 모호한 필드만 빠른 선택 또는 음성 후속 답변 → 장소 검색·인라인 지도 확인 → 한 번 탭해 확정
- 음성 날짜: 시간만 말하면 오늘, 요일만 말하면 이번 주 해당 요일, 월·일을 말하면 해당 날짜로 설정
- 음성 대체 입력: 음성 화면의 `키보드로 직접 입력·수정` → 추출된 값이 채워진 직접 수정 폼
- 음성 할 일: `보고서 작성해야 해` → 할 일로 분류 → 2~5분 행동 최대 3개 확인·부분 수정 → `저장하고 5분만 시작` → `지금–다음–나중` → 현재 행동 완료 후 다음 행동 전환
- 계획 확정: AI 계획 확인 → `이 계획으로 시작` 없음 → `계획 확정` → 일정 목록 저장
- 다중 계획: 같은 날 두 계획 확정 → 일정 목록에 두 카드 유지 → 앱 재실행 후에도 복원
- 예약 실행: 준비 시작 전 진행 화면 미생성 → 시작 시각에 앱 안에서 자동 실행 → 백그라운드에서는 예약 알림 후 복귀 시 실행 상태 복구

`src/data/demo.ts`를 시각/상호작용 검증 fixture로 사용한다.

| ID | 상태 | 기대 결과 |
|---|---|---|
| H-01 | 다음 일정 있음 | 14:00 약속, 12:55 준비 시작, 4분 여유 |
| P-01 | 정상 진행 | 현재 행동과 카운트다운, 다음 행동 표시 |
| P-02 | 6분 지연 | 해결 배너와 변경된 도착 시간 표시 |
| P-03 | 추가 5분 | 남은 계획 즉시 재계산, 변경 단계 표시 |
| B-01 | 플랜 B | 현재 수단을 제외한 대중교통/택시 예상안과 TMAP 도보 실제 경로 비교 |
| C-01 | 완료 | 실제 대비 요약과 다음 계획 추천 |

시간 의존 테스트에서는 시스템 현재 시각 대신 fixture 시각을 주입한다.

## 수동 스모크 테스트

1. 홈의 `새 일정 추가`에서 3단계를 끝낸다.
2. AI 계획에서 시간 요약과 세로 타임라인, `계획 확정` 버튼을 확인하고 `이 계획으로 시작`이 없는지 확인한다.
3. 계획을 확정해 일정 목록에 저장되는지 확인한다. 확정된 준비 계획의 여유 시간은 도착 시간 오른쪽에 두 줄로 표시되고 장소명 옆의 중복 도착 예정 문구는 없어야 한다. 장소명 오른쪽의 `지도 보기`를 누르면 도착 장소 지도가 아코디언으로 펼쳐지고 다시 접을 수 있어야 한다. 전체 타임라인의 이동수단은 아이콘·테두리·배경과 텍스트로 즉시 구분되며 수단별 아이콘은 카드 오른쪽 끝에 있어야 한다. 하단에는 굵고 큰 원형 체크와 `약속이 저장됐습니다.` 문구가 표시되고 카드 전체를 누르면 홈으로 이동해야 한다. `약속 수정`은 기존 값을 유지한 편집 화면과 재확인을 거쳐 같은 저장 항목을 교체하고, `약속 삭제`는 확인 전까지 유지한 뒤 확인 시 예약 알림과 함께 제거해야 한다. 같은 날 두 번째 계획도 확정한 뒤 두 건이 함께 유지되고 앱 재실행 후 복원되는지 확인한다.
4. 준비 시작 시각 전에는 진행 세션이 생기지 않고, 해당 시각에 앱이 열려 있으면 자동 실행되는지 확인한다. 앱이 백그라운드라면 예약 알림을 확인하고 앱 복귀 시 실행 상태가 복원되는지 확인한다.
5. 실시간 진행에서 완료 후 현재 단계가 다음 단계로 이동하는지 확인하고, `시간 더 필요`에서 +5분을 선택해 지연 문구와 변경 표시를 확인한다.
6. 플랜 B에서 예상 대안에 `예상값`, 도보 실호출에 `TMAP 실제 경로`가 표시되고 시간·거리·비용·환승 정보를 확인할 수 있는지 확인한다.
7. 택시의 `변경 내용 확인`을 눌러도 아직 현재 경로가 유지되고, 확인 카드의 `이 경로 적용`을 누른 뒤에만 진행 화면으로 이동하는지 확인한다.
8. 적용 후 앱을 강제 종료·재실행하고 플랜 B를 열어 `현재 경로 · 택시`가 복원되고 택시가 대안 목록에서 제외되는지 확인한다.
9. 완료 화면에서 홈으로 돌아가 데모가 초기화되는지 확인한다.
10. 일정 화면에서 `완료` 탭을 눌러 완료 기록이 표시되는지 확인한다.
11. 플랜 B의 `걷기 최소`를 눌러 걷기 시간이 짧은 예상안이 먼저 정렬되는지 확인한다.
12. 등록 3단계에서 준비 행동을 추가하고 저장된 목록에 나타나는지 확인한다.
13. 설정에서 여유 시간을 변경한 뒤 앱을 다시 열어 선택값이 유지되는지 확인한다.
14. 권한 화면에서 앱 설명을 확인한 뒤에만 위치 권한 요청 버튼을 누른다.
15. 위치를 거부해 수동 출발지를 저장하고 설정 화면에 같은 값과 거부 상태가 표시되는지 확인한다.
16. 위치를 다시 거부해 차단 상태와 기기 설정 이동 버튼이 표시되는지 확인한다.
17. 알림을 거부하거나 앱 알림을 끈 뒤 앱 내 진행 안내 fallback 문구를 확인한다.
18. 진행 화면에서 `이동 경로 보기`를 열고 `도보 · TMAP 경로`, ETA, 약속까지 시간, km/m 거리, 다음 행동이 표시되는지 확인한다.
19. 이동 화면의 `음성 안내 끄기/켜기`를 눌러 문구·접근성 레이블이 함께 바뀌고 앱 오류가 없는지 확인한다.
20. 앱을 백그라운드로 보낸 뒤 복귀해 위치·경로가 재조회되고, 네트워크 차단 시 마지막 안내·임시 경로·재시도 버튼이 유지되는지 확인한다.
21. 신규 설치/저장 초기화 상태에서 온보딩 3장의 다음·이전·건너뛰기를 확인하고 마지막 `첫 일정 만들기`가 일정 등록 1단계에 진입하는지 확인한다.
22. 온보딩 완료 후 앱을 다시 실행해 온보딩이 반복되지 않는지 확인한다.
23. Journey의 `화면 꺼짐 안내 켜기` 전에 위치 사용 간격·로컬 저장·중지 방법이 표시되는지 확인한다.
24. Android 위치 상세 화면에서 `항상 허용`을 선택하고 앱으로 돌아와 `켜짐`과 위치 foreground-service 상단 알림을 확인한다.
25. 앱을 백그라운드로 보내거나 화면을 끈 뒤 새 위치 event에서 마지막 갱신 시각과 음성 전달 상태가 바뀌는지 확인한다.
26. 백그라운드 TTS 실패 시 동일 행동·ETA·거리가 OS 알림으로 전달되는지 확인한다.
27. `화면 꺼짐 안내 끄기`와 목적지 도착에서 foreground service, task 등록, `@on-time/background-journey` 저장값이 모두 제거되는지 확인한다.
28. 하단 내비게이션 가운데 음성 버튼으로 연 음성 일정 화면에서 화면을 열자마자 `실시간 대화 · 자동 듣기 · 켜짐`이 표시되고 첫 질문 TTS 뒤 별도 터치 없이 자동 녹음되는지 확인한다. 대답 뒤 약 0.8초 침묵에서 자동 제출→AI 응답 TTS→다음 자동 듣기가 반복돼야 한다. 수동 종료 버튼은 없어야 하며, 소음이 많은 곳에서도 발화가 끝나면 자동 제출돼야 한다. 기기가 음량을 보고하지 않으면 약 4초 뒤 자동 제출하고, 어떤 경우에도 한 턴은 15초 안에 끝나야 한다. 발화 없는 빈 녹음은 서버로 보내지 않고 다시 들어야 한다. `내일 3시 강남에서 병원, 1시간 전에 출발`은 제목·날짜·시간·장소·준비시간 카드로 추출되고, 장소 검색 결과와 인라인 지도에서 위치를 확인할 수 있어야 한다. `금요일 오후에 치과`는 시간만 질문하며 13:00·15:00·17:00·직접 입력을 제공하고, 선택 뒤 기존 제목·날짜를 유지해야 한다. 카드의 시간 또는 세부 설정만 직접 수정할 수 있고 모든 필수값·장소 좌표 확인 뒤 `확정하고 일정 등록` 한 번으로 저장돼야 한다. 마이크 거부·네트워크 오류에는 재시도와 키보드 직접 수정 경로를 제공해야 한다.
29. 설정에서 화이트·다크 모드를 바꾼 뒤 음성 화면의 배경·텍스트·버블·탭이 함께 바뀌고 앱을 다시 열어도 선택값이 유지되는지 확인한다.
30. 일정 화면의 `캘린더` 탭에서 사전 설명을 확인한 뒤 권한을 허용하고, 실제 Google·Apple/iCloud 또는 기기 캘린더의 향후 30일 일정과 공급자 필터가 표시되는지 확인한다.
31. 시간 일정을 선택해 카드 바로 아래 미리보기를 확인하고 `이 일정 가져오기` 전에는 기존 초안이 유지되며, 누른 뒤에만 제목·날짜·시간·장소가 새 일정 1단계에 반영되는지 확인한다.
32. 종일 일정을 가져와 약속 시간이 빈칸이고 시간을 입력하라는 다음 행동이 표시되는지 확인한다. Android APK에는 `READ_CALENDAR`만 포함되고 `WRITE_CALENDAR`가 없는지도 함께 확인한다.
33. 설정의 `Plus 미리보기`에서 완료 3회 전 남은 횟수, 완료 3회 후 가격안 선택, 적용 전 저장 불변, 관심 등록, 앱 재실행 복원, 철회 확인 전 유지와 확인 후 삭제를 확인한다. 화면에는 결제·자동 갱신·연락처 수집이 없고 기능이 출시 후보임이 표시돼야 한다.
34. Plus 미리보기에서 `나와 가까운 사용자 유형`을 고르고 화면을 닫는다. 선택은 다시 열었을 때 유지돼야 하고, 닫는 시점에 집계값이 서버로 전송돼 관리자 통계에 이 계정 한 행으로 남아야 한다. 앱에는 공유 버튼도 Phase 0 결과 화면도 없어야 하며, 계정을 삭제하면 그 행도 함께 사라져야 한다.
35. 오늘·내일·모레·과거 시각의 확정 계획과 기기 캘린더 일정을 함께 저장하고 앱을 다시 연다. 홈의 `오늘·내일 약속` 제목 아래 오늘과 내일 항목만 날짜·시간순으로 노출되며 모레 이후 계획은 `내 일정`에만 남아야 한다. 과거 예약·실행 중 계획은 `지난 일정`에서 `미완료`, 모든 준비 행동을 끝낸 계획은 `완료` 텍스트로 표시되며 앱 재실행 뒤에도 상태가 유지돼야 한다.
36. 정시 완료 5건을 연속으로 저장한 뒤 홈을 다시 연다. `오늘·내일 약속` 목록 끝에 주황색 아이콘과 `연속 5회 정시 도착 중`, `한 번만 더 하면 '시간의 달인' 뱃지야`, `보기`가 텍스트로 표시돼야 한다. `보기`를 누르면 `지난 일정` 탭이 열리고 각 일정의 `정시 도착/지각 도착/완료/미완료` 상태가 색상 없이도 구분돼야 한다. 최근 결과 앞에 지각 또는 미완료 기록을 추가하면 그 이전 정시 기록은 현재 연속 횟수에 포함되지 않아야 하며, 완료 화면에서 홈으로 돌아간 뒤에도 기록이 유지돼야 한다.
37. 음성 화면에서 `보고서 작성해야 해`라고 말했을 때 날짜·장소를 요구하지 않고 할 일로 분류하는지 확인한다. 최대 3개의 행동이 각각 2~5분으로 제안되고 첫 행동을 수정한 뒤 `저장하고 5분만 시작`을 누르면 즉시 카운트다운과 감소형 바, `지금–다음–나중`이 표시돼야 한다. 앱을 다시 열어도 활성 할 일과 종료 시각이 유지되고 현재 행동 완료 후 다음 행동이 `지금`으로 이동해야 한다.
38. 20분 이상인 준비 행동이 포함된 계획을 확정해 실행한다. 다음 행동 15분 전에는 현재 행동 마무리 예고, 5분 전에는 새 일을 벌이지 말라는 마무리 알림, 종료 시에는 완료 확인과 다음 행동이 순서대로 예약돼야 한다.
39. 준비 행동이 끝나는 알림을 알림창에서 펼친다. `다음 행동 시작`과 `5분 더 하기` 버튼이 함께 보여야 한다. `다음 행동 시작`을 누르면 앱을 열지 않고도 현재 행동이 완료 처리되고 다음 행동이 `지금`으로 바뀌어야 한다. `5분 더 하기`를 누르면 현재 행동의 남은 시간이 5분 늘고 이후 알림이 그만큼 뒤로 다시 예약돼야 한다. 이미 지나간 행동의 알림에서 버튼을 눌러도 현재 행동이 건너뛰어지지 않아야 한다.
40. 설정의 `준비 단계 음성 코치`를 켠 상태로 계획을 실행한다. 두 번째 이후 준비 행동이 시작될 때마다 소리가 나는 알림이 오고, 진행 화면이 열려 있으면 지금 할 행동과 배정 시간, 다음 행동을 한 문장으로 말해야 한다. 마지막 준비 행동에서는 다음 행동 대신 마지막이라고 알려야 한다. 토글을 끄면 단계 시작 알림과 음성이 모두 멈추고 종료 알림은 남아야 하며, 앱을 다시 열어도 선택이 유지돼야 한다.
41. Android에서 설정의 `알림 및 권한 > 준비 알람 정확도`를 연다. 카드에 정확한 시각 알람과 배터리 최적화 상태가 텍스트로 보이고, `정확한 시각 알람 허용`은 시스템 `알람 및 리마인더` 화면을, `배터리 최적화 예외 설정`은 시스템 예외 대화상자(또는 목록)를 열어야 한다. 돌아오면 상태가 다시 읽혀야 한다. 두 설정이 켜진 상태로 2분 단계를 실행하고 앱을 백그라운드로 보낸 뒤 화면을 꺼 두면, 단계 종료 시각에 `… 예정 시간이 끝났어요` 알림이 알람 소리와 함께 제시간에 도착해야 한다(`adb shell dumpsys alarm`에서 `com.timeagent.app` 알람이 `window=0`인지 확인). 정확한 시각 알람을 끄면 진행 화면 알림 상태 아래에 알람이 늦을 수 있다는 안내와 `알람 설정 확인`이 나타나야 한다.
42. 홈에서 새 일정을 직접 입력으로 연다. 약속 시간은 `오전/오후`·`시`·`분` 세 개의 드럼을 위아래로 밀어 고르고, 손을 떼면 가운데 띠에 값이 정확히 맞춰지며 아래 문장(`오후 1:35 · 위아래로 밀어서 고르세요`)이 바뀌어야 한다. 드럼의 값을 직접 눌러도 선택돼야 하며, TalkBack에서는 각 드럼이 하나의 조절 컨트롤로 읽히고 위·아래 스와이프로 값이 바뀌어야 한다. 날짜 행(`오늘 · 8월 23일 (일)`)을 누르면 달력이 펼쳐지고 지난 날짜는 눌리지 않아야 하며, 날을 고르면 달력이 닫히고 행의 날짜가 바뀌어야 한다. 요일 칩(일~토)을 켜면 `매주 화`처럼 요약이 바뀌고 날짜가 그 요일의 첫 날로 이동해야 하며, `매일`·`평일`·`주말`은 한 번에 여러 요일을 켜고 `반복 끄기`는 모두 꺼야 한다. 반복 약속을 확정하면 홈·일정 카드에 `매주 화 반복`이 보이고, 그 약속이 끝나거나 지나가면 같은 시간의 다음 회차가 예정 목록에 자동으로 생겨야 한다(다음 회차를 삭제하면 반복이 멈춘다).
43. 홈 상단에 인사말·날짜·약속 수 헤더 줄이 없고 약속 상자(또는 안내 상자)가 바로 보여야 한다. 하단 내비게이션 가운데에 음성 일정 버튼이 `약속` 라벨과 함께 바의 윗변에 반쯤 걸친 채 고정돼 홈·일정·알림·설정 어느 탭에서도 같은 자리에 있어야 하고, 누르면 음성 일정 화면이 열려야 하며, 화면을 끝까지 스크롤해도 콘텐츠가 버튼 뒤로 가려지지 않아야 한다.
44. 오늘 이미 확정된 약속(예: 12:57 볼링, 샤워 포함)이 있는 상태에서 같은 날 약속을 하나 더 만들고(더 늦은 시각이든 이른 시각이든) 준비 행동 단계로 가면 `오늘 두 번째 약속이에요` 카드와 함께 샤워·스킨케어·화장·면도·헤어 정돈 가운데 그 약속이 이미 가진 항목이 목록에서 빠지고, 어느 약속 준비에 이미 있는지 한 문장이 보여야 한다. 그대로 `AI 계획 만들기`를 누르면 계획·타임라인에도 샤워가 없어야 한다. `샤워 다시 넣기`를 누르면 샤워가 원래 자리로 돌아오고 그 칩만 사라지며, 그 계획에는 샤워가 남아야 한다. 같은 날 다른 약속이 없거나 다른 약속에 샤워가 없으면 이 카드가 나타나지 않아야 하며, 음성으로 바로 확정한 두 번째 약속도 같은 규칙으로 준비 행동이 줄어야 한다.
45. 홈 상단은 상자 없이 좌측 끝의 모서리 라운드 삼각형(▶)+`시작` 라벨 버튼과, 그 오른쪽에 큰 글씨 두 줄(`41분 후 준비` / `알람이 울립니다`, 진행 중에는 `약속 제목` / `진행하고 있어요`), 그 아래 작은 글씨로 `오늘 화요일 약속 1개 · 내일 1개` 약속 개수를 보여야 한다(버튼·문구 모두 실시간 준비 화면을 연다). 등록 약속 목록 위에는 제목 텍스트 없이 `+` 버튼만 오른쪽에 있다. 약속 목록의 약속 시간은 예전의 두 배 크기(36px)이고 상태 표시(`실행 중`/`N시 시작`/`알람 꺼짐`)는 좌측 시간 아래 `오늘` 라벨 옆에 있으며, 각 항목 오른쪽의 알람 스위치를 끄면 그 계획의 준비 알람·5분 전 알림·자동 시작이 모두 멈추고 `알람 꺼짐` 표시와 함께 흐려지며, 다시 켜면 알람이 재예약돼야 한다. 목록의 모든 알람을 끄면 상단이 `켜진 준비 알람이 없어요`로 바뀌어야 한다. 홈에는 `오늘의 준비 계획` 타임라인 구역이 없고, `오늘·내일 등록 약속 N개` 제목 오른쪽에는 `전체 보기` 대신 `+`(새 일정 직접 등록) 버튼이 있어야 한다.
46. 현재 위치 날씨 카드는 홈이 아니라 알림 화면 맨 위에 있어야 한다. 권한 없음·네트워크 실패의 복구 행동과 카드 터치 시 날씨 상세 이동은 알림 화면에서 그대로 동작해야 한다. 확정 약속이 없는 홈에는 `말로 새 일정 만들기` 버튼 없이 안내 상자 하나만 보이고, 안내는 `일정을 등록하면 준비 시작 시각에 자동으로 실행돼요.` 한 줄이며 상자를 누르면 일정 생성 화면이 열려야 한다.
47. 일정 화면의 `내 일정` 탭은 상단(제목·탭)은 그대로 두고 그 아래에 폰 기본 달력식 월 달력을 보여야 한다. 일정이 있는 날에는 점이 찍히고, 날을 고르면 그 날의 일정 카드만 아래에 나열되며, `오늘` 버튼과 이전/다음 달 이동이 동작해야 한다. 텍스트 줄(`내 일정 화면입니다.`) 오른쪽 끝의 `+` 버튼은 직접 입력 일정 등록 화면을 열고, 이 탭의 `말로 새 일정 만들기` 버튼은 없어야 한다.
48. 이동수단 선택지는 등록 화면·설정·음성 확인 모두 `AI 추천(설정 제외)`·`대중교통`·`승용차(택시)`·`도보`뿐이어야 한다. 예전에 저장된 버스·지하철·택시·자가용 값은 앱을 열면 각각 대중교통·승용차(택시)로 읽혀야 하고, 계획 타임라인의 출발 단계는 `대중교통으로 출발`/`승용차로 출발`로 표기돼야 한다. 설정의 성별을 남성으로 두면 새 일정 기본 준비 항목에 화장이 없고 면도가 있어야 한다.
49. 준비 시작 5분 전에 `약속 준비 시작 5분 전이에요` 알림이 소리와 함께 도착해야 하고, 앱이 열려 있으면 같은 문장을 음성으로도 말해야 한다(알림 꺼짐·화면 읽기 사용 중에는 음성 생략). 약속을 삭제하면 5분 전 알림도 함께 취소돼야 한다.
50. 내일 이후 날짜의 대중교통 약속을 만들어 계획 화면을 연다. `이동 시간 근거` 카드에 `지하철 24분 · 1,450원 · 환승 1회 · 도보 8분`처럼 소요시간·요금·환승·도보와 `TMAP 시간표 기준 · HH:MM 계산 · HH:MM 출발 기준`이 텍스트로 보여야 한다(자동차는 `실시간 교통 기준`, 도보는 `도보 경로`, 조회 실패 시 `거리 기반 예상`). 약속 시각이나 목적지를 바꾸면 이전 근거가 사라지고 새로 조회돼야 한다. `첫 탑승 · 노선 · 정류장` 줄에는 출발 30분 전까지 `시간표 기준`, 그 뒤 버스는 `실시간 · HH:MM 확인`(TAGO 키 등록 시)과 `N분 후 (M정류장 전)`, 지하철·미지원 지역은 `시간표 기준 · HH:MM 확인`과 이유 문장이 보여야 한다. 실시간이 시간표보다 3분 넘게 늦으면 출발·도착 전후 시각과 `플랜 B에서 대안 보기`/`이대로 유지`가 제안되고, 적용 전에는 계획·알림이 바뀌지 않아야 한다. `다시 확인`은 20초 안에 다시 눌러도 같은 값을 보여야 하고, `네이버 지도에서 보기`는 앱이 있으면 앱, 없으면 브라우저 길찾기를 열어야 한다(카카오맵 버튼은 2026-08-27에 뺐다).
51. 새 일정 3단계 `무엇을 준비해야 하나요?`에서 각 준비 행동의 시간은 `−`/`+` 버튼이 아니라 좌우로 미는 드럼(`11분 · 12분 · 13분`)으로 고른다. 손을 떼면 가운데 띠에 값이 맞춰지고 총 준비 시간이 즉시 바뀌어야 하며, 드럼의 보이는 값을 눌러도 선택돼야 한다. TalkBack에서는 드럼이 하나의 조절 컨트롤로 읽히고 `1분 늘리기`/`1분 줄이기` 동작으로 값이 바뀌어야 한다. 세로 스크롤 화면 안에서 좌우 드럼을 밀어도 화면이 세로로 끌리지 않아야 한다.

## Android Play 출시 빌드

업로드 키 암호는 macOS Keychain에서 읽으며 명령행이나 저장소에 남기지 않는다. 키 파일과 Keychain 항목이 준비된 Mac에서 다음을 실행한다. 명령은 먼저 Expo prebuild를 실행해 추적되는 `plugins/with-timeagent-release.js`의 서명·최소 권한 설정을 생성된 Android 프로젝트에 적용한다.

```bash
npm run release:android
```

산출물은 `android/app/build/outputs/bundle/release/app-release.aab`과 `android/app/build/outputs/apk/release/app-release.apk`다. Android 실기기용 `armeabi-v7a`와 `arm64-v8a`를 포함한다. 릴리스 작업은 업로드 키 환경값이 하나라도 없으면 실패하며 debug 키로 대체 서명하지 않는다. 제출 절차와 외부 차단 항목은 `docs/RELEASE_CHECKLIST.md`를 따른다.

Play App Signing 등록 후에는 Play의 앱 서명 인증서 SHA-1을 Google Android OAuth 클라이언트에 추가하고, 내부 테스트 트랙에서 로그인 왕복을 다시 확인한다.

### Google 로그인 설정 점검

Google Cloud에서 Web OAuth 클라이언트와 Android OAuth 클라이언트를 만든 뒤, Web 클라이언트 ID를 `.env.local`에 설정한다. Android 클라이언트에는 진단 결과에 표시되는 패키지명과 SHA-1을 그대로 등록해야 한다. 기기가 연결돼 있으면 진단기는 Play 설치 여부, 설치 버전, 실제 전달 APK의 서명 SHA-1도 표시한다. Play Console에 현재·이전 앱 서명 키가 함께 있으면 Android 버전에 따라 어느 키든 전달될 수 있으므로 각 SHA-1마다 같은 패키지명의 Android OAuth 클라이언트를 별도로 등록한다.

```bash
npm run auth:doctor
```

모든 항목이 준비된 뒤 새 APK를 빌드·설치하고 다음 왕복을 실제 Google 계정으로 확인한다.

1. 앱 데이터 삭제 후 실행하면 Google 로그인 화면만 표시된다.
2. Google 계정 선택을 취소하면 오류로 처리되지 않고 로그인 화면에 머문다.
3. 계정을 선택하면 홈으로 진입하고, 앱 강제 종료·재실행 뒤에도 세션이 복원된다.
4. 설정에서 계정 이메일을 확인하고 로그아웃하면 즉시 로그인 화면으로 돌아간다.
5. 네트워크를 끈 로그인 실패에는 재시도 가능한 다음 행동이 텍스트로 표시된다.

```bash
cd android
./gradlew app:assembleDebug -PreactNativeArchitectures=arm64-v8a
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb reverse tcp:8083 tcp:8083
```

NAVER 지도 의존성을 받으려면 `app.json`의 `expo-build-properties`에 `https://repository.map.naver.com/archive/maven`이 유지돼야 한다. 지도 타일은 NAVER Cloud Maps의 Android 패키지 허용 설정까지 별도로 검증한다.

## 시각 회귀 매트릭스

각 핵심 화면을 360x800, 390x844, 430x932에서 라이트 모드로 캡처한다. 최소 대상은 홈, 직접 수정 폼, 음성 자동 듣기·추출 결과·모호성 질문, 캘린더 일정, 정상/지연 진행, 플랜 B, 완료, 설정, Plus 미리보기다.

### 세 기준 화면 시각 회귀

Playwright 브라우저를 최초 한 번 설치한다.

```bash
npx playwright install chromium
```

기준 이미지와 현재 화면을 비교한다.

```bash
npm run visual:test
```

의도한 디자인 변경을 검토한 뒤에만 기준 이미지를 갱신한다.

```bash
npm run visual:update
```

`playwright.config.mjs`가 Expo web server, 한국 시간대, 고정 모바일 viewport를 준비한다. `e2e/visual/app.visual.spec.mjs`는 홈·직접 수정 폼·음성 자동 듣기/추출 결과/모호성 질문·AI 계획·개인화 계획·MVP 지표·Plan B·Journey fallback/화면 읽기·완료·설정·Plus·정상/지연 진행을 검증하며 기준 PNG는 `e2e/visual/__screenshots__/`에 보관한다. 각 테스트는 가로 넘침과 기준 이미지 대비 0.2% 초과 차이를 실패로 처리한다.

확인 항목:

- 텍스트/CTA 잘림과 겹침 없음
- 키보드 표시 중 다음 CTA 접근 가능
- 하단 내비게이션과 기기 safe area 충돌 없음
- 폰트 200% 확대 시 핵심 상태 문구 유지
- 색상 제거 상태에서도 정상/지연/오류 구분 가능

Maestro 흐름은 `e2e/maestro/`에 두고 고정 시나리오 ID를 테스트 이름에 사용한다.

## 실패 처리

- 테스트를 삭제하거나 완화해 통과시키지 않는다.
- 환경 문제와 제품 회귀를 분리해 기록한다.
- 재현 가능한 최소 fixture를 먼저 추가한 다음 수정한다.
- `npm audit fix --force`는 Expo 호환성을 깨뜨릴 수 있으므로 자동 실행하지 않는다.
